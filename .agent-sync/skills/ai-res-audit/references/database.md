# Database audit procedure

- Read shared database conventions before the engine sheet and observed ORM deltas. Apply actual engine/version semantics: nullability/unique keys, defaults, coercion, precision/rounding, collation/timezone and installed constraints. Follow primary documentation linked from the conventions; inspect relevant settings/extensions.
- Inventory tables, columns, ownership paths, keys/cardinalities, closed sets/transitions, immutable versions, copied facts, views, migration/export paths and main queries. Trace consumers, authorization, concurrency and retries; distinguish database guarantees from application guards not implemented yet.
- For plans, apply the evidence-based plan-review matrix. For implementations, inspect migrated definitions where accessible. Schema text alone cannot prove installation, permissions or runtime behavior.
- Add isolated probes only for concrete risks: wrong uniqueness scope, nullable/composite/partial keys, conditional values, omitted exported constraints, conversion/calculation errors, access control or transaction races. A duplicate test uses the same non-NULL business key on otherwise valid distinct rows; reuse existing sufficient evidence.
- Verify exact defaults and SQL/driver/API round trips when behavior proof is warranted. Preserve correctness without unjustified redundant identifiers/snapshots.
- Use real project query shapes: bounded pagination, N+1/round trips, index predicates/order, redundancy, views and prepared-query lifecycle. Removing an index must preserve uniqueness, predicates and required access paths; no measured gain without representative evidence.
- In execution modes, apply inspected migrations only to a disposable same-engine target. A local owner role does not prove production RLS/permissions; actual concurrency needs independent connections. Record unavailable recovery/restore and provider evidence separately, without attempting restoration or real side effects on live targets.

## Required schema-warning evidence
- Apply [database warning triage](../../../../code-conventions/database.md#351-schema-warning-triage-and-intentional-exceptions), including all seven warning families and previously ignored findings. REQUIRED report section: tool/model revision and engine, inventory coverage (including unavailable suppressed items), named targets/rules, intended invariant, exact source/verification evidence, disposition, residual consequence and exception decision/recheck conditions.
- Assess `CORRECTED`, `JUSTIFIED_EXCEPTION`, `FALSE_POSITIVE` or `UNRESOLVED` per item; use the existing plan matrix for proposed decisions and distinguish planned corrections/checks from implemented proof. Missing evidence cannot justify Ignore or waive database integrity/tenant isolation. Report unresolved items and coverage gaps explicitly even when the visual warning counter is zero.
- Reconcile diagram/export warnings with authoritative DDL and actual writers/query paths; never force NOT NULL/defaults/indexes or duplicate owner keys solely to silence a heuristic. In review mode do not click Ignore or mutate editor state; propose an evidence-backed disposition for an authorized editor task, retaining its rationale outside the editor.
